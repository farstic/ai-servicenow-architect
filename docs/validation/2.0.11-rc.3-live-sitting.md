### R1 to R4 — the storage the tools assume (reads)

**The shipped "Jasmine Successful Test".** One step, at order 1. Its two `sys_variable_value` rows each have:
- `document = sys_atf_step`;
- `document_key` = the step;
- `variable` = the input variable;
- `value` (the script, about 1 KB, and "3.1");

**Verdict on the reads:** the column names and the storage shape are the ones the tools assume. CONFIRMED.

**Observed — the test index "ignored my name filter".** `snow_atf_atf_tests_index` declares no name argument:
its schema is `suite_sys_id`, `active` and `limit`. The server checks no argument against a tool's schema, so
an argument it does not declare is dropped silently. The query sent was `sys_atf_test`, `active=true`, with
the default limit 20 (`src/tools/atf.ts:224`). This was not the instance ignoring a condition. The exact call,
from the owner's transcript: at 06:44:59Z, `snow_atf_atf_tests_index { "query": "name=Jasmine Successful Test" }`.
The undeclared `query` was dropped, and the tool answered the 20 active tests. The Architect picked the Jasmine
test from the list and noted that the filter had been ignored. This is opened as ARC-09-C121.

**Follow-up read, before the teardown:** the new step has two `sys_variable_value` rows.

The shipped step's two rows are both at order 100.

The tool's output named only `script`, so a teardown built from it would miss the `jasmine_version` row. This is

### Teardown

Each removal was approved on its own.

1. **`snow_core_record_remove` on the script's `sys_variable_value` row: refused by the instance.** The answer:
   "Cannot delete sys_variable_value/<id>: it is referenced by other records (reference/cascade constraint)…
   ServiceNow detail: ACL Exception Delete Failed due to security constraints (Code: DELETE_CONSTRAINT)". The
   Architect neither retried nor worked around it. Whether the cause is an ACL or a reference constraint is not
   established; the corpus is silent on it.
2. **`snow_core_record_remove` on the step: deleted.** A read of `sys_variable_value` by `document_key` then
   counted 0: both input rows, `script` and `jasmine_version`, went with the step.
3. **`snow_core_record_remove` on the test: deleted.**
4. **The capture target.** A read-only lookup found the global Default update set (one row, with `is_default`
   false; the Architect noted that the capture preference does not depend on that flag). Then
   `snow_us_capture_target_set` answered `updated`: the same preference record, pointed back at Default.
5. **The update set** `demo-pdi-c95` was set to Ignore in the UI by the owner. Its two entries presumably now
   record the deletes; they were not looked at.
