**Pass condition, first half (no `warnings` key):** met. A check that warned on every write would have shown
one here.

**Second half (no `Querying ServiceNow table: sys_dictionary` line in the server's stderr log): NOT

the startup banner and one `Calling MCP tool` / `completed` pair per call — **no `Querying ServiceNow table`
line at all, for any call, including step 1**, which did look up `sys_dictionary` (`confirmed: true`). Absence
in step 3 therefore proves nothing: the info-level query log does not reach this file. A way to see it would
be to start the server with its log at info level on a terminal.

**Corroboration from the audit trail** (`.local/audit.jsonl`, tool/result/warnings keys only): step 1's line
carries `warnings: [{ code: "VALUE_TRUNCATED", table: "sys_script", fields: ["name"], count: 1 }]`; step 3's

**What the procedure asks to record — does the entry's payload carry the corrected name?** The preview lists
the entries but not their payloads, so the `sys_update_xml` rows for this update set were read with
`snow_core_records_query` (a read):

- **One entry per rule, not one per write.** The step 3 rule was written three times and has ONE row; its
  payload is the LATEST version: `<name>c93-live-probe-short</name>`, `<sys_mod_count>2</sys_mod_count>`.
  So a correcting modify made while the same update set is the capture target does leave the corrected
  name as the entry's content — which is what the warning message tells the user to do.

- The REST-created objects were captured at all: the §2.2 chain works for `sys_script` on this instance.
