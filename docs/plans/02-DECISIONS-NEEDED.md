## D-01 — Product, repository, CLI and server names

> **DECIDED 2026-09-04 — (a)(b)(c) confirmed as recommended; (d) AMENDED by the owner.** (a) `farstic/ai-servicenow-architect` · (b) `snowarch` · (c) MCP key `servicenow` → tool prefix `mcp__servicenow__` · (d) **`@farstic/snowarch` — a brand-new npm record** (availability verified 2026-09-04: `npm view @farstic/snowarch` → not published). **Owner constraint:** the existing `@farstic/snow-mcp@1.0.0` on npmjs is **never touched** — no new version, no deprecation, no unpublish, no README edit; anything the unified product publishes goes under a totally new package. Consequences: the server+CLI package directory is `packages/snowarch` (not `packages/snow-mcp`), its `bin` is `snowarch`, and `npx @farstic/snowarch` yields the CLI and the stdio server — one name across repo-package/CLI/npm. `engine.config.json` records all four values; ARC-01/ARC-04/ARC-05/ARC-09 use them. **Confirmed by the owner 2026-09-04: `@farstic/snowarch`.**

**Question.** Which single set of names does the unified product use? Four names are needed: (a) the GitHub repository, (b) the product / CLI short name (it becomes the command `./snowarch`, the optional global config directory `~/.config/<name>/`, and the `/<name>`-style skill prefix if a plugin channel is added later), (c) the MCP server key (it becomes the literal tool prefix `mcp__<key>__` that the §2.1 write gate, permission rules and hook matchers are generated from), (d) the server package name.

**Recommendation.**
- (a) `farstic/ai-servicenow-architect` — matches the product the user knows ("AI ServiceNow Architect"), avoids the current three-way mismatch (`AI-Architect-Claude` / `claude-servicenow-live` / NowAIKit — `00` P-15).
- (b) `snowarch` — short, lowercase, typeable, no collision on npm or in Claude Code's bundled skills.
- (c) `servicenow` — descriptive; tools read `mcp__servicenow__snow_core_records_query`; and it is what Design B/C and two judges assumed. (`snow` would give `mcp__snow__snow_…`; `servicenow-mcp` would preserve today's working-tree `CLAUDE.md` text but is longer for no benefit.)
- (d) `@farstic/snow-mcp` — you already own this scoped name on npm (`npm view @farstic/snow-mcp` → 1.0.0, maintainer farstic; verified 2026-09-04); the unscoped `servicenow-mcp` and `servicenow-mcp-server` belong to third parties (`00` §4.1).

**If you choose otherwise.** All four values live in `engine.config.json` and are read by the doctor, the lint, the generators and the launchers; changing any of them is a one-line edit plus a regeneration — provided the choice is made before ARC-05 generates the governance texts. The server key must contain only letters, digits, `-` and `_` (`docs:mcp` on `add-json` keys). The directory name a user clones into does **not** have to match the repository name (the design uses `${CLAUDE_PROJECT_DIR}` everywhere).

## D-02 — Licence of the unified repository (and relicensing of snow-mcp)

> **DECIDED 2026-09-04 — Apache-2.0 for the whole repository.** The author confirms this is a personal project (no employer IP claim), so relicensing is a unilateral author statement. Deliverables: one root `LICENSE` (Apache-2.0), a `NOTICE` carrying the ServiceNow / ServiceNowDocs Apache-2.0 attribution, the relicensing sentence in the first commit message, and removal of the contradictory `smithery.yaml` MIT claim and the engine's "Proprietary" wording. ARC-01 owns this.

**Question.** Under which licence is the new public repository published, and do you, as copyright holder, relicense the snow-mcp code so it may be merged? Today `snow-mcp/LICENSE` **prohibits copying, modifying, merging and derivative works**, `smithery.yaml` claims MIT, and the engine's `docs/README.md` says "Proprietary … not licensed for redistribution" (`00` P-32). The merge is impossible under the current texts, and the repository embeds an Apache-2.0 corpus (ServiceNowDocs) whose attribution must ship.

**Recommendation.** **Apache-2.0** for the whole repository (engine + server), one `LICENSE` at the root, a `NOTICE` carrying the ServiceNow/ServiceNowDocs attribution, and a one-line relicensing statement in the first commit message ("snow-mcp and claude-servicenow-live relicensed by their author under Apache-2.0"). Apache-2.0 aligns with the corpus, includes an explicit patent grant, and is the licence consultancies and clients accept without review. MIT is an acceptable alternative if you prefer the shorter text.

**If you choose otherwise.** *Source-available / proprietary:* the repository can still be private or source-available, but the "public repo any user points Claude at" goal narrows to invited users, GitHub marketplace/plugin distribution (§17 roadmap) becomes impractical, and `NOTICE` obligations for ServiceNowDocs still apply. *No relicensing of snow-mcp:* ARC-04 cannot start; the server would have to be rewritten from the public REST API surface rather than merged.

## D-04 — Credential-at-rest policy and authentication methods in 1.0

> **DECIDED 2026-09-04 — (a) yes: one per-checkout store `.local/instances.json` (dir 0700, file 0600, gitignored, atomic writes, never in `~/.claude.json` / argv / transcripts); OS-keychain backend stays roadmap item 3. Rationale recorded: per-checkout (not per-user) is deliberate — it aligns with the engine's client confidentiality firewall (one engagement = one checkout = one store). Added obligation for ARC-07/ARC-08: the wizard and the doctor must WARN when the checkout path lies under a known cloud-sync folder (OneDrive, Dropbox, iCloud Drive, Google Drive), because 0600 does not prevent sync. (b) Basic auth is the wizard default; OAuth password grant is kept as an "Advanced" branch labelled "OAuth (password grant, legacy)"; client-credentials grant stays roadmap item 4.

**Question.** (a) Is one plaintext JSON file per checkout — `.local/instances.json`, directory 0700, file 0600, gitignored, atomically written, never copied into `~/.claude.json`, argv or a transcript — acceptable for 1.0, with an OS-keychain backend as a later opt-in? (b) Which authentication methods does the 1.0 wizard offer: basic only, or basic plus the OAuth password grant (ROPC) that the server already implements?

**Recommendation.** (a) **Yes for 1.0.** It is the same protection class as today's `~/.claude.json` (which is also plaintext) but with exactly one copy, correct file modes, and no argv/backup exposure — a strict improvement — and it needs no native module. The keychain backend (`@napi-rs/keyring`) is §17 roadmap item 3. (b) **Basic + ROPC, labelled honestly.** Basic is the PDI reality (zero instance-side setup; `00` §7.1). ROPC is offered as "OAuth (password grant, legacy)" because it still requires a user password plus a client id/secret and ServiceNow's own docs classify it as legacy with a hardening switch that disables it (`00` P-38). The client-credentials grant (no user password) is §17 item 4 because it needs new server code and instance admin work.

**If you choose otherwise.** *Keychain mandatory from day one:* ARC-07 gains a native dependency (`@napi-rs/keyring` prebuilt binaries per OS/Node ABI), macOS Keychain prompts for `node`, and a fallback file is still needed for headless CI — +1 sprint and a Windows/Linux credential-store test matrix. *Basic only:* removes ~300 lines from the wizard and the OAuth probe from the doctor; existing OAuth users of snow-mcp lose the mode until client-credentials ships.

## D-05 — Default permission posture and production safeguards

> **DECIDED 2026-09-04 — confirmed WITH A MODIFICATION from the owner.** (a) **Changed:** for `pdi` / `dev` / `test` instances the system *proposes* the `full` preset (every capability on), not `read-only`; the user reviews a per-flag screen where each flag is pre-set ON and annotated with its live probe result, and may toggle any flag or switch preset before anything is saved. A failing probe changes only the recommendation text on that line, never the toggle. `read-only` remains the proposal for `prod`. (b) **Unchanged:** `prod` is capped at `read-only`; raising it requires `./snowarch instance set-preset <label> <preset> --ack-prod` with the label typed, and the server refuses a `prod` instance with a write preset unless `prodWriteAck: true` is in the store. Environment detection: `^https://dev\d+\.service-now\.com` → proposed `pdi`; everything else is asked, never guessed. **Owner directive recorded as design principle 10 in `01` §2 ("Propose, don't impose"):** the user must be involved in the whole configuration process — the system proposes at every step, the user can change any value at any level, and the whole experience must be intuitive, easy and fast. This is now an acceptance criterion for ARC-06 and ARC-07 and the `01` §6.3 preset flow was rewritten accordingly.

**Question.** Should the wizard (a) default every new instance to the `read-only` preset, pre-selecting `pdi-developer` only when the instance is tagged PDI or Development, and (b) hard-cap instances tagged Production to `read-only`, so that raising them requires a separate explicit command (`./snowarch instance set-preset <label> <preset> --ack-prod`, typing the label) and the server refuses to start a Production instance with a write preset unless the store entry carries the acknowledgement? Today your own registration is all-write (WRITE, SCRIPTING, CMDB_WRITE, ATF on) with two flags absent (`00` §5).

**Recommendation.** **Yes to both.** It matches governance §2.1 (writes are exceptional and explicit), makes the safe path the short path, and costs a PDI user exactly one Enter (the pre-selected `pdi-developer`). The prod cap is what a consultancy security reviewer expects and what the audit log (`.local/audit.jsonl`) then documents.

**If you choose otherwise.** *Replicate today's all-write posture as default:* the preset table stays, only the default changes — but the doctor will then WARN on every all-write prod instance, and the plan's security claims in `01` §7 must be softened. *No prod cap:* remove the `prodWriteAck` rule from ARC-04/ARC-07; the environment tag becomes informational only.

## D-06 — Accept the bounded interruptions of the chosen channel (now) rather than wait for the plugin channel

> **DECIDED 2026-09-04 — accepted (1)–(4) for 1.0, WITH A HEDGE.** The plugin-channel spike set S-14 is pulled forward into ARC-00 and must complete **before ARC-06 starts** (not after 1.0). If S-14 proves the eleven plugin behaviours within its time-box, the channel decision is re-opened before any bootstrap investment; if not, ARC-06 proceeds on the verified monorepo path with no time lost. ARC-00's exit criteria and ARC-06's entry criteria are updated accordingly. The `/setup-instance` skill must guide the user through the terminal hand-off for credentials from inside Claude (say exactly what to type, wait, resume) so interruption (3) never leaves the user without a next step.

**Question.** The chosen design cannot be literally "zero interruptions". It guarantees: no hand-edited JSON, no build step, no path discovery, one resumable command, design-only in one run with no Node. It still contains: (1) Claude Code's workspace-trust dialog on the first `claude` in a new folder (unavoidable for any cloned repository — `docs:mcp`); (2) possibly one approval click for the project MCP server if the pre-seeded `enabledMcpjsonServers` is not honoured on the very first launch (S-01 — the docs fetched 2026-09-04 say an untracked `.claude/settings.local.json` approval is applied as soon as the trust dialog is accepted, so the expected count is one dialog); (3) credentials typed in **your own terminal**, not inside Claude (the only channel that keeps them out of the transcript and argv); (4) on the "start Claude in an empty folder and point it at the repo" path, one restart of `claude` after the clone. The plugin/marketplace channel (Design A) would remove (3) by using Claude Code's masked `userConfig` dialog, but rests on eleven behaviours that have never been exercised (S-14) and attaches the server at user scope by default.

**Recommendation.** **Accept (1)–(4) for 1.0** and schedule the plugin channel as §17 roadmap item 1 once ARC-00's spikes prove it. Shipping a verified path first, then adding the smoother channel, is lower risk than betting 1.0 on the plugin behaviours.

**If you choose otherwise.** *Plugin channel first:* ARC-00 must run the full S-14 spike set before any other ARC starts (≈ 1 week); the repository layout changes to a marketplace with two plugins; `CLAUDE.md`'s protocol moves into a SessionStart injection; the tool prefix becomes `mcp__plugin_<name>_servicenow__`; multi-instance still needs the file store; and installation defaults to `--scope project` with explicit documentation. The judges' totals (A 129 vs B 138) reflect that trade.
