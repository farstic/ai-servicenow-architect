## 1. The design in one paragraph

One GitHub repository, `farstic/ai-servicenow-architect`, is the product. Its root is the Claude Code project a consultant clones and runs `claude` in: a thin `CLAUDE.md`, the 28 skills and 9 sub-agents in their single canonical location (`.claude/`), the governance texts, a **committed, secret-free `.mcp.json`** that registers the bundled MCP server at project scope through `${CLAUDE_PROJECT_DIR:-.}` (so `git clone` *is* the registration and nothing is ever written to `~/.claude.json`), a committed `.claude/settings.json` with a SessionStart hook that prints the authoritative `Mode:` line, and a **prebuilt server** under `packages/snowarch/dist/` (no TypeScript compile at install time). Everything that cannot be committed — the docs corpus, Node dependencies, credentials, permission flags, per-machine toggles — is produced by one idempotent, resumable bootstrap (`./bootstrap.sh` / `bootstrap.cmd`) that completes **design-only mode with no Node.js at all** and, when asked for a live instance, runs a masked-input wizard in the user's own terminal, writes one 0600 store inside the checkout, probes the instance immediately, and writes the settings toggles that make the next `claude` start clean. The engine and the server share one version, one git tag, and one machine-readable **contract** generated by the server and pinned by the engine; tests on both sides make silent drift impossible.

## 2. Design principles (Decided)

1. **Design-only is the default end state**, not a fallback: a passing doctor with the server disabled is a complete install.
2. **Every piece of wiring that can be committed is committed** (`.mcp.json`, `.claude/settings.json`, `dist/`, the contract). Every piece that cannot be is produced by the bootstrap and verified by the doctor.
3. **Secrets never enter argv, transcripts, `~/.claude.json`, git, or the plugin cache.** They are captured only by masked input in the user's own terminal and stored once, 0600, inside the checkout.
4. **One vocabulary**: *Mode* (`design-only` | `live`) and *Preset* (`read-only` | `pdi-developer` | `full` | `custom`). The word "Tier" is retired everywhere.
5. **One version, one tag, one contract.** No independent counters; drift fails CI on whichever side forgot.
6. **One runtime for shipped tooling: Node ≥ 20.** Bash and PowerShell survive only as ~100-line launchers for the Node-free design-only path.
7. **The server is a server.** Desktop app, other-client writers, BYOK direct mode, reports, A2A, dashboard, HTTP/SSE transport, prompt capabilities and Copilot personas leave the product (D-03).
8. **Sub-agents never call MCP tools** (explicit `tools:` lists retained); only the main thread, under §2.1, touches a live instance.
9. **Two Claude Code dialogs are budgeted, never promised away**: the workspace-trust dialog on first `claude` in a folder, and possibly one approval of the project MCP server (S-01 tests whether the bootstrap's pre-seeding removes it).
10. **Propose, don't impose (owner directive, 2026-09-04).** Every configuration step — bootstrap and wizard alike — follows *Propose → Review → Apply*: the system shows its proposal with a one-line reason, the user accepts it with Enter or edits any single value before it is applied, and everything remains re-editable afterwards (`./snowarch instance …`, `/snowarch setup-instance`). Nothing is applied without being shown first. The fast path is therefore "press Enter through sensible proposals"; the involved path is "change any line". Reconciled with principle 1 and the "no interruptions" goal as follows: *installation* (clone, deps, build, registration) runs uninterrupted after one up-front plan summary the user can amend; *configuration* (instances, presets, flags) is always interactive with proposals. `--yes` accepts every proposal non-interactively for CI and re-runs. This principle governs ARC-06 and ARC-07 and is an acceptance criterion for both.

Design-only without Node: the launcher performs B00 (git + claude only), B01, B02 (checkout and area-existence check only; citations are verified once Node is present), B07, B09 itself; the Node-only steps are skipped and the summary says "doctor unavailable until Node 20+ is installed". The launcher writes `.local/bootstrap-state.json` (mode, docs pin, timestamp) so that `/snowarch status` can still report `Mode: design-only` from that file when the doctor cannot run (§8). **Typed user actions: 2 pastes (the one-line clone + bootstrap, then `claude`) — 4 if typed line by line. Dialogs: trust (always) + MCP approval (only if S-01 fails). No JSON is edited by hand at any point.**

## 5. MCP registration mechanism (with evidence)

**Mechanism: a committed project-scope `.mcp.json` at the repository root.** Exact content:

```json
{
  "mcpServers": {
    "servicenow": {
      "type": "stdio",
      "command": "node",
      "args": ["${CLAUDE_PROJECT_DIR:-.}/packages/snowarch/dist/server.js"],
      "env": {
        "SNOW_STORE": "${SNOW_STORE:-}",
        "SNOW_LOG_LEVEL": "${SNOW_LOG_LEVEL:-info}"
      },
      "timeout": 600000
    }
  }
}
```

Companion, committed `.claude/settings.json`:

```json
{
  "env": { "MCP_TIMEOUT": "120000" },
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume",
        "hooks": [
          { "type": "command", "command": "node",
            "args": ["${CLAUDE_PROJECT_DIR}/tools/snowarch/hooks/session-start.mjs"],
            "timeout": 10 }
        ]
      }
    ]
  },
  "permissions": {
    "allow": [
      "Bash(./snowarch doctor*)",
      "Bash(node tools/snowarch/bin/snowarch.mjs *)",
      "mcp__servicenow__snow_core_capabilities_read",
      "mcp__servicenow__snow_core_instances_index",
      "mcp__servicenow__snow_core_instances_reload",
      "mcp__servicenow__snow_core_current_instance_read"
    ],
    "ask": [
      "mcp__servicenow__snow_core_record_add"
    ]
  }
}
```

ARC-05 generates the rest of both permission blocks from the contract: `allow` receives every `mutates:false` tool (explicit names, or globs if S-12 passes) so reads never prompt; `ask` receives every `mutates:true` tool. The `ask` block is what makes §2.1 mechanical rather than prose: on Pro, Max and Team plans a session starts in **auto mode**, where a classifier — not the user — approves tool calls, but an action matching an explicit `ask` rule resolves to a user prompt before the classifier is consulted (`docs:permission-modes`, "How the classifier evaluates actions", step 1). Without it a mutating MCP call could run with no "write approved" from the user. S-18 verifies the prompt appears in auto mode.

Why this works, each point docs- or CLI-verified on 2026-09-04:

| Claim | Evidence |
|---|---|
| A project `.mcp.json` is loaded for any session started in the folder and shared through version control | `docs:mcp` "Project scope" |
| `${VAR}` / `${VAR:-default}` are expanded in `command`, `args`, `env`; `CLAUDE_PROJECT_DIR` is set in the **server's** environment, so the docs themselves prescribe `${CLAUDE_PROJECT_DIR:-.}` in project entries | `docs:mcp` "Option 3: Add a local stdio server" |
| An unset `${VAR}` *without* a default is passed to the server as the literal string — hence every placeholder carries `:-` and the doctor fails any that does not | Design B's probe on CLI 2.1.258 (recorded in the evidence base); `docs:mcp` warns about missing variables in `claude mcp list` |
| The approval prompt for project servers exists and is reset by `claude mcp reset-project-choices`; `claude -p` loads them without asking | `docs:mcp` "Project scope" |
| `enabledMcpjsonServers` in `.claude/settings.local.json` is **exactly what Claude Code writes when the user approves a server in the dialog**; `disabledMcpjsonServers` rejects and wins; in an untrusted folder only the shared project file is ignored | `docs:settings-reference` `enabledMcpjsonServers`, `disabledMcpjsonServers` |
| `MCP_TIMEOUT` governs server startup; timeout-class `env` values in `.claude/settings.json` apply at startup from every settings file; per-server `timeout` is the per-call wall clock | `docs:mcp` tips; `docs:settings-reference` `env` "When Claude Code applies env values" |
| Exec-form hooks with `command: node` + script path run on every platform; `${CLAUDE_PROJECT_DIR}` is substituted in each `args` element; `.cmd` shims cannot be spawned on Windows | `docs:hooks` exec form note |
| Tools are named `mcp__servicenow__<tool>`; permission rules accept globs only after the literal `mcp__servicenow__` prefix | `docs:mcp`; `docs:permissions` |
| `list_changed` from the server refreshes tools without reconnecting | `docs:mcp` "Dynamic tool updates" |

Consequences: `git clone` is the registration; `claude mcp add` is never run; `~/.claude.json` is never touched; moving or renaming the checkout cannot lose the server; the registration key `servicenow` is a contract value read by the rule file, the permission list, the doctor and the lint (never hand-written). Fallback for users under managed policies that block project servers: `./snowarch mode live --register local` runs `claude mcp add-json servicenow '<same secret-free JSON>' -s local` (this checkout only, stored in `~/.claude.json`; verified on 2.1.258: `add-json` accepts `-s local|user|project`). `--register user` exists as a last resort but attaches the server to every project on the machine, which the engagement firewall argues against.

The server never sees a secret through `.mcp.json`: it reads `SNOW_STORE` if set, otherwise `<CLAUDE_PROJECT_DIR ?? cwd>/.local/instances.json`, otherwise `~/.config/snowarch/instances.json` (the optional global store), otherwise it starts **unconfigured** (§9).

## 6. Post-install instance wizard

### 6.1 Surface recommendation and why

The owner asked for a recommendation — an "installation widget" or something else — for the guided path that adds an instance with the right permissions. **Recommended surface: a terminal CLI command owned by the server package (`snowarch instance add`), fronted inside Claude Code by the `/snowarch setup-instance` skill; no widget.** The alternatives were evaluated against the evidence:

| Surface | Verdict | Reason |
|---|---|---|
| Inside Claude Code via Bash | not possible | Claude's Bash tool is non-interactive; masked input cannot run there |
| `AskUserQuestion` | non-secrets only | answers are recorded in the transcript |
| MCP elicitation | non-secrets only | the MCP spec forbids elicitation for sensitive data |
| HTTP dashboard / `web` UI | rejected | requires an already-configured instance to boot, unauthenticated by default, not an admin plane (`00` §4.7) |
| Electron desktop app | rejected | decrypts its keychain secrets back into plaintext, needs per-OS packaging/signing, never registers a client |
| Plugin `userConfig` (sensitive) | deferred channel | strongest secret channel, but holds one configuration set per plugin and the plugin channel carries the spikes in S-14 (§17 roadmap) |
| Terminal CLI with masked prompts | **chosen** | the only place a secret can be typed without transcript, argv or file exposure; reusable by non-Architect users; testable in the server's CI |
| One-shot localhost form | roadmap | same security class; for environments where the terminal is shared or recorded |

### 6.2 Step-by-step UX

Entry points: automatically as bootstrap step B06 when live mode is chosen; later `./snowarch instance add` in a terminal; or `/snowarch setup-instance` inside Claude Code.

`/snowarch setup-instance` (skill, user- and model-invocable):
1. Runs `./snowarch doctor --json --section prereqs` (pre-authorised in `permissions.allow`): Node ≥ 20 and server deps present. If not: "Node.js 20+ is required for live mode — install it (macOS `brew install node@22`; Windows `winget install OpenJS.NodeJS.LTS`; Linux distro package or nvm), then `/snowarch setup-instance` again." and stops.
2. `AskUserQuestion` #1 — *Which kind of instance?* PDI · Development · Test · Production.
3. `AskUserQuestion` #2 — *Authentication?* Basic (username + password; default; zero instance-side setup; recommended for PDI) · OAuth password grant (legacy ROPC; needs an OAuth API endpoint, client id + secret **and** a user password; ServiceNow classifies it as legacy and Security Center hardening can disable it) · Client-credentials grant (listed as a roadmap option, not selectable — `AskUserQuestion` cannot grey an option out).
4. `AskUserQuestion` #3 — *Permission preset?* (table of §6.3; Production pre-selects and defaults to Read-only).
5. In chat: instance URL (validated as a bare `https://` origin — vanity hostnames allowed, trailing slash stripped, `/api` rejected with the reason) and a short label (e.g. `pdi`), and whether it becomes the checkout's default instance.
6. Prints the exact command with every non-secret value pre-filled and asks the user to run it in their own terminal:
   `./snowarch instance add pdi --url https://dev12345.service-now.com --env pdi --auth basic --preset pdi-developer --default`
7. The CLI then prompts `Username:` and `Password:` (masked; raw-mode stdin, no echo; OAuth adds `Client ID:` / `Client secret:`), probes `GET /api/now/table/sys_user?sysparm_limit=1` (10 s HEAD reachability first, with DNS / TLS / proxy diagnosis), and on 401 says "AUTHENTICATION_FAILED — wrong username or password. Re-enter? (attempt 2 of 3)" — a bounded loop, never a silent retry (account-lockout risk); on 403 explains missing roles. There is no "save anyway". It then runs the per-preset capability probes (`sys_update_set`, `sys_script_include`, `cmdb_ci`, `sys_atf_test`, `sys_properties` `sn_generative_ai*` when NOW_ASSIST) and reports each `ok` / `role missing`, writes the store atomically (0600), and prints a secret-free summary: `Saved instance "pdi" (pdi · basic · preset pdi-developer · default). Probes: auth ok · write ok · scripting ok · cmdb ok · atf ok.`
8. Back in Claude: `/snowarch setup-instance --resume` (or "done"). The skill calls `snow_core_instances_reload` (server re-reads the store and emits `tools/list_changed`), then `snow_core_capabilities_read`, then `./snowarch doctor --json`, and prints the authoritative line: `Mode: live — pdi (pdi) · preset pdi-developer · WRITE=on CMDB_WRITE=on SCRIPTING=on ATF=on NOW_ASSIST=off FLUENT=off · 398 tools`. No session restart. If the tool list does not refresh (S-02), the skill says "run `/mcp` → servicenow → reconnect".
9. It closes with the §2.1 reminder: writes need an explicit "write approved" message; §2.2 sets the update-set capture target before any configuration write.

Second instance: repeat with another label (`./snowarch instance add uat …`); `snow_core_instance_switch` switches, with per-instance flags evaluated at call time (ARC-04). Maintenance: `./snowarch instance list` (label, environment, preset, last probe — never secrets), `test <label>`, `set-preset <label> <preset>`, `set-credentials <label>`, `remove <label>`. Wrong password at runtime: the server returns `AUTHENTICATION_FAILED`; the rule file tells the engine to stop (no retries) and point to `./snowarch instance set-credentials <label>`.

### 6.3 Permission presets (plain language)

Every preset writes **all six** flags as the byte-exact strings the server compares against (`"true"` / `"false"`), plus `toolPackage: "full"` and `maxRecords: 100`. The dependency rule (SCRIPTING and CMDB_WRITE require WRITE) is enforced in the UI and again in the server.

| Preset | WRITE | CMDB_WRITE | SCRIPTING | ATF | NOW_ASSIST | FLUENT | Use it when… |
|---|---|---|---|---|---|---|---|
| `read-only` | false | false | false | false | false | false | Auditing, reviewing, designing against a real instance; **the only preset a `prod` instance may hold without `--ack-prod`** |
| `pdi-developer` | true | true | true | true | false | false | Building on a PDI / dev / test instance when Now Assist or Fluent are not wanted |
| `full` | true | true | true | true | true | true | Everything on; **the system's proposal for every `pdi` / `dev` / `test` instance (D-05)**; NOW_ASSIST needs a licence, FLUENT needs `@servicenow/sdk` — both are probed and annotated before the user confirms |
| `custom` | six explicit toggles | | | | | | Anything else; dependency rule enforced |

**Proposal and review flow (D-05 as decided, applying principle 10).** The wizard never silently applies a preset. For a `pdi` / `dev` / `test` instance it *proposes* `full` — the owner's directive is that non-production environments start with every capability available — then shows a per-flag review screen in which each of the six flags is pre-set ON, annotated with the live probe result, and individually toggleable:

```
Proposed preset for "pdi" (pdi): full  — non-production: everything on
  [x] WRITE        probe: ok
  [x] CMDB_WRITE   probe: ok
  [x] SCRIPTING    probe: ok
  [x] ATF          probe: ok
  [x] NOW_ASSIST   probe: no Now Assist licence detected — tools will fail until licensed; keep on? (recommend: off)
  [x] FLUENT       probe: @servicenow/sdk not on PATH — keep on? (recommend: off)
Enter = accept as shown · type a flag name to toggle · "preset <name>" to switch preset
```

A probe that fails downgrades the *recommendation* shown on that line; it never flips the toggle by itself — the user decides. Whatever leaves this screen is written as six explicit strings. For a `prod` instance the proposal is `read-only` and the review screen shows the write flags greyed out with the `--ack-prod` instruction. Environment detection: a URL matching `^https://dev\d+\.service-now\.com` is proposed as `pdi`; any other host is *asked* ("What is this instance? pdi / dev / test / prod"), never guessed. All of this is re-runnable later via `./snowarch instance set-preset`, `set-flags`, or `/snowarch setup-instance`.

What each flag means, as shown to the user:

- **WRITE** — lets the engine create, update and delete records (incidents, catalog items, users, agile work, update sets). Without it everything is read-only.
- **CMDB_WRITE** — additionally allows CI and relationship reconciliation writes into the CMDB.
- **SCRIPTING** — unlocks *writing* Script Includes, Business Rules, Client Scripts, ACLs, UI Actions and update-set changes. *Reading* them is always allowed (split by ARC-04-S05, 2026-09-08).
- **ATF** — lets the engine *execute* ATF tests and suites (authoring and reading are always allowed).
- **NOW_ASSIST** — enables the Now Assist / generative-AI tools; needs a Now Assist licence on the instance.
- **FLUENT** — enables the ServiceNow SDK (Fluent) build/deploy tools; needs `@servicenow/sdk`; deploys also need WRITE.

Safety rules (Decided; posture defaults are D-05): an instance tagged `prod` cannot be given anything above `read-only` in the wizard; raising it requires `./snowarch instance set-preset <label> <preset> --ack-prod` and typing the label; the server refuses to start a `prod` instance with a write preset unless the store entry carries `prodWriteAck: true`.

## 7. Credential storage (Decided; at-rest policy is D-04)

- **Where:** one file per checkout, `<checkout>/.local/instances.json`, directory 0700, file 0600, written by atomic rename; gitignored. Optional global store `~/.config/snowarch/instances.json` (`%APPDATA%\snowarch\instances.json` on Windows) via `instance add --global` for a personal PDI shared across checkouts; the project store wins when both exist; they are never merged. Deleting the checkout deletes its credentials. Windows: user-profile ACL; the doctor reports "file modes: ACL-inherited".
- **Schema v1:** `{ "version": 1, "defaultInstance": "pdi", "instances": { "pdi": { "url", "environment": "pdi|dev|test|prod", "auth": { "method": "basic|oauth_ropc", "username", "password" | "clientId", "clientSecret", "username", "password" }, "preset", "flags": { six explicit strings }, "toolPackage": "full", "maxRecords": 100, "prodWriteAck": false, "lastProbe": { "at", "auth", "write", "scripting", "cmdb", "atf", "nowAssist" } } } }`.
- **How captured:** only by `snowarch instance add|set-credentials` in the user's terminal (raw-mode masked input) or `--password-stdin` for automation. Never via Claude's Bash tool, `AskUserQuestion`, elicitation, `claude mcp add -e`, or a CLI flag.
- **How never leaked:** `.mcp.json` is secret-free by construction and the doctor fails if it or any `.claude/settings*.json` contains a key matching `/PASSWORD|SECRET|TOKEN|_KEY$/i`; `snowarch` output and the SessionStart banner mask usernames (`c***@corp.com`) and print `set (len n)` for secrets; the server refuses a group/world-readable store and prints the `chmod 600` remedy; `REDACT_SENSITIVE_DATA` defaults to on and the Authorization header is never logged; the server's cwd `dotenv.config()` is removed (explicit `SNOW_ENV_FILE` only); a CI grep fails on credential-shaped literals anywhere in the tree; the legacy `~/.config/servicenow-mcp/instances.json` is never read (the doctor offers a one-time import, ARC-10).
- **Audit trail:** the server appends one JSON line per mutating call to `.local/audit.jsonl` — timestamp, instance label, tool, table, sys_id or query, result code; never payload values, never credentials; rotated at 10 MB; `./snowarch audit tail` prints it. This makes §2.1 "write approved" provable after the fact.
- **Roadmap** (§17): OS-keychain backend (`@napi-rs/keyring`) as an opt-in; OAuth client-credentials grant so no user password is stored for non-PDI instances.

## 11. Contract and drift prevention (Decided)

**The contract is generated by the server, pinned by the engine, and enforced on both sides.**

- Every tool registration in `packages/snowarch/src` declares `gate: 'none'|'write'|'scripting'|'cmdb_write'|'atf'|'now_assist'|'fluent'` and `mutates: boolean`. `scripts/extract-tools.mjs` (already guarding 394 unique names) emits `dist/tools-manifest.json` (now with `gate`/`mutates`) and `dist/contract.json`: `{ contractVersion, server: { suggestedName: "servicenow" }, flags: [{ name, exactString: "true", absentMeans: false, requires: [] }], errorCodes: [], tools: [{ name, gate, mutates }], presets: { read-only, pdi-developer, full }, protocols: { updateSetCapture: [ordered calls] }, maxRecordsDefault: 100 }`.
- Engine side: `packages/contract/required-tools.json` lists 41 tools — the 35 engine-cited tools, `snow_us_update_set_preview` (required by the §2.2 capture protocol) and the five core tools — with `used_by` (`§2.1`, `§2.2`, `developer`, `code-reviewer`, …) and pins `contractSha256`.
- **Server test** (`packages/snowarch/tests/contract.test.ts`, extending the existing `parity.test.ts` throwing-Proxy pattern): every catalogue tool, with all flags unset, throws exactly the code implied by its declared gate (or reaches the client for gate `none`); with each preset applied, gated tools pass; every mutating-suffixed tool has `mutates: true`; manifest and contract list identical names; `tool-rename-map.json` values ⊆ catalogue; rebuilt `dist/` equals committed `dist/`.
- **Engine lint** (`packages/contract/lint/engine-lint.mjs`): every `snow_[a-z0-9_]+` and `mcp__[a-z0-9-]+__` token in `CLAUDE.md`, `.claude/`, `governance/`, `docs/`, `tools/` must exist in the pinned contract; the prefix must equal `mcp__servicenow__`; no key of `retired-names.json` as a bare word; every skill description ≤ 500 chars; `claude plugin validate .claude/skills` and `.claude/agents` pass; the generated files (`.claude/rules/00-mode-and-mcp-gate.md`, `governance/mcp-protocols.md`, the `permissions.allow` block, `docs/TROUBLESHOOTING.md`) are byte-identical to their generators' output.
- **Tooling** reads flag names, presets, error codes and tool names from the contract; nothing hard-codes a list.
- A release cannot be tagged unless all three pass; a scheduled job re-verifies citations against the docs pin.

§2.2 becomes shorter and testable: the server gains `snow_us_capture_target_set` (writes `sys_user_preference` name=`sys_update_set` for the authenticated user — the platform behaviour field-notes §1 confirms) and `snow_us_active_update_set_ensure` gains a mandatory name and a current-user filter. The generated protocol is: ensure/create the named update set → set the capture target → perform the write → verify in `sys_update_xml`.

## 16. Why not the alternatives

Three independent judges scored the three candidate designs (0–10 per criterion, six criteria, max 60):

| Design | End user | Security | Maintainer | **Total** |
|---|---|---|---|---|
| A — Plugin-native (marketplace repo, two plugins, `userConfig` secrets) | 47 | 42 | 40 | **129** |
| **B — Monorepo + one-shot bootstrap (chosen spine)** | 45 | **47** | **46** | **138** |
| C — Provider/Consumer (the server package on npm, thin engine pins it) | 41 | 38 | 42 | **121** |

Per-criterion detail (simplicity / robustness / security / maintainability / native fidelity / feasibility): A = 8-7-9-8-9-6 · 7-7-6-9-8-5 · 8-6-8-6-8-4; B = 7-9-7-8-7-7 · 7-9-8-8-8-7 · 7-9-8-8-7-7; C = 7-6-7-8-7-6 · 7-6-6-7-6-6 · 8-6-7-7-8-6.

Why B: it is the only design whose critical path was **exercised** on the current CLI (project `.mcp.json` + `${CLAUDE_PROJECT_DIR:-.}` + `${VAR:-default}` expansion, cwd = project directory), whose secrets never leave the user's terminal, whose upgrade story is operable (resumable steps with input hashes), and whose blast radius stays inside the checkout (project scope; no user-scope anything). Both the security and the maintainer judge chose it outright; the end-user judge preferred A by two points for its in-window masked secret dialog but scored A lowest on feasibility.

Why not A (now the §17 roadmap channel): plugins cannot ship `CLAUDE.md`, so the governance core would ride on an unmeasured ~12 KB SessionStart injection; `userConfig` holds one configuration set per plugin, so the second instance falls back to a file anyway; the default `claude plugin install` scope is *user*, attaching a write-capable server and hooks to every project on the machine — the opposite of the engagement firewall; the tool prefix changes to `mcp__plugin_<p>_<s>__`; eleven load-bearing behaviours are unverified (S-14). Its best ideas were grafted: unconfigured server mode and `snow_core_capabilities_read`, prod write acknowledgement at process level, the blobless/sparse docs recipe, the description cap, credential-literal lint, removal of cwd `dotenv`.

Why not C: the engine's MCP entry would download ~27 MB (post-cut; 72 MB today) from the npm registry **inside the server-startup window of the user's first session** — silent failure on a proxied laptop, no lockfile/integrity pin in the engine, and the one published artefact (`@farstic/snow-mcp@1.0.0`) has no verifiable provenance. Its best ideas were grafted: the contract generated at build from per-tool declarations, `retired-names.json` as a forbidden-word list, the wizard and live doctor living in the server package, two doctors merged into one report, `engine.config.json`, and the optional provenance-signed npm publish as a *secondary* channel.
