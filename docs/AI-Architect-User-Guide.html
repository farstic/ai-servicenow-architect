Before you begin

About this guide

This guide is for ServiceNow consultants — business analysts, architects and developers — who have installed the AI Architect with the install guide for their computer. It shows everything you can do with it afterwards: work with it every day, connect and look after your ServiceNow instances, keep it healthy and up to date, and recover when something goes wrong.

It describes release v2.2.6. A few things exist only in the next release: they are marked New in 2.2.7.

Pick one. The guide shows the commands for that computer, and remembers your choice. You can switch at any time, also at the foot of the Contents.

■How to read this guide

  • Run every command in or , inside your AI-Arch folder, outside Claude — unless the guide says Inside Claude. The install guides make that folder in your home folder: ~/AI-Arch or C:\Users\<you>\AI-Arch. If yours has another name, use it wherever this guide says AI-Arch.
  • Each dark box with a Copy button holds exactly one command. Click Copy, click inside the Terminal or PowerShell window, paste with Command+V or a right-click (or Ctrl+V) and press Return or Enter. The square on the left of a box ticks itself when you copy.
  • A word above a box says when it applies. Optional: you can skip the command. zsh or bash: the command differs by shell, so run only the one for your Terminal. Git Bash: run it in a Git Bash window, not in PowerShell (Engagements and client folders shows how to open one).
  • Where the guide says the key alone at a question, press Return or Enter without typing anything first.
  • The AI Architect's own screens say Enter. On a Mac that is the Return key.
  • On a Mac: the AI Architect's command is ./snowarch. Wait until the line that ends in % comes back before you run the next command. (If your Terminal uses bash, the line ends in $ instead.)
  • On Windows: the AI Architect's command is .\snowarch.cmd. PowerShell refuses a bare snowarch.cmd, so keep the .\ in front. Wait until the line that starts with PS comes back before you run the next command. In Git Bash the command is ./snowarch, as on a Mac.
  • Commands that start with /, such as /mcp, are typed inside Claude, and so is the plain word Status. Most messages quoted in this guide spell the command ./snowarch, as the AI Architect prints it inside Claude and in Git Bash. In PowerShell, always type .\snowarch.cmd, whatever a message says.
  • Words in angle brackets are placeholders. <label> is your instance label, <you> your user name on the computer, https://<name>.service-now.com your instance address, and <name> in clients/<name> a client's short name. Others are explained where they first appear. Replace the whole placeholder, brackets included, before you press Return or Enter. Where a command uses your instance label, engagement name or licence file, it takes them from Your details: until you type yours there, the boxes show the samples pdi, acme and LIC-2026-0000.json.
  • To change part of a command, paste it but do not press Return or Enter yet. Press the left arrow key until the cursor is just after the part to change, press delete or Backspace until that part is gone, type yours, then press Return or Enter.
  • Dark boxes labelled On screen show what you will see. You do not type those. A purple part is what you type, and ❯ is Claude's prompt. Press ▶ Play to watch them typed out. They are examples: your numbers, dates, times and names differ.
  • Before each command the guide says what it does: whether it only reads, or what it changes. After it, the guide says what you should see.
  • Type with an English (Latin) keyboard layout: the keys you type by hand at a question — y, n, q, a number, a label — must arrive as Latin letters. If you use another alphabet, switch the keyboard layout first.
  • This guide uses the English names of menus and folders. On a computer set to another language they appear translated; the commands stay the same.
Never paste several commands at once

Paste one, press Return or Enter, wait, then the next.

Never as an administrator

Run every command as yourself: never with sudo, which would run it with the administrator's rights or never in a window opened with Run as administrator. A line that starts with PS C:\WINDOWS\system32> is an administrator window: close it and open a normal one. The AI Architect's commands never need administrator rights.

Something unexpected on the screen?

Do not press Return or Enter. Press Control+C (the control key and C together, not the command key) or Ctrl+C to cancel, then look it up in Troubleshooting.

■Status: is everything right?

  • The Doctor: line counts the quick health check. A warning is named only by its id, for example 1 warn (E-23); a failure gets its own line with its remedy. See Health checks.
  • Instances: lists the instances saved in this folder, with default on the one new sessions start on. It reads the saved list; it does not connect to them.
  • On this quick run, the Mode line names the first instance in the saved list. That is not always the default, nor the one this session works on. To know where the session works now, ask: Which instance is this session on?

■Restart Claude

Claude reads the AI Architect's settings, its connection and your licence when a session starts. After some changes you restart it: type /exit, then, in the same folder, claude. To reload only the connection to your instance, type /mcp, choose servicenow › reconnect.

Restart after you install or renew a licence; after mode live or mode design; after an upgrade; when the Integrity line ends with — restart claude; after you set proxy or certificate settings; and after a change of where the connection is registered. Adding or changing an instance needs no restart (see Make an open session see a change). A new session does not carry the conversation over.

Working with the AI Architect

You describe what you need in plain words; that is the whole interface for design work. The AI Architect — the Chief Architect, with its specialists — routes your request to the right specialist, reviews what comes back and hands you the result. Chat in Bulgarian or English; deliverables are written in professional English.

■How to ask

  • Name the module when it is obvious: ITSM, CSM, HRSD, ITOM.
  • Name the release. Say Australia release, so the AI Architect does not recommend a feature you do not have. On another release family it confirms with you before a version-sensitive answer.
  • Give the context: volumes, how sensitive the data is (personal, financial, regulated), the workspace or portal, the roles, the other systems involved.
  • Name the engagement, so it reads that client's context and writes the results into that client's folder (see Engagements and client folders).

Expect questions before a deliverable: the AI Architect surfaces its assumptions and open questions first, even when that slows the answer. It says plainly when a request goes against ServiceNow practice, and what to do instead. It does not state a table, a feature or a mode from memory: what it says about ServiceNow comes from the bundled documentation, with the page it read (see ServiceNow documentation).

■What happens to a request

For every substantial request you see these steps in the first reply, in this order:

  1. Restatement. The task in one sentence.
  2. Engagement context. If you named a client, it reads that client's engagement-state file and the Envelopes it lists.
  3. Assumptions and open questions. The engagement's defaults are applied silently; only real uncertainty becomes an OPEN QUESTION with a proposed default.
  4. Custom objects. If the request needs a custom table, a scoped app, a new state or another major custom object, it says so here (see The baseline-first rule).
  5. Domain gateway. For an ITSM, CSM, HRSD, ITOM, CMDB and CSDM, or FSO Insurance task, that domain's gateway writes a in the same reply, at Phase 1 Step 5.
  6. Routing and consults. It settles which specialist fits, and names the cross-cutting consults the request triggers.
  7. Proposal. A Proposal: line: the specialist, or several in order, the consults, and a one-line reason.
  8. Your approval. It waits for you. Nothing is built before you approve.
  9. The build, the review, the result. The specialist works with the task, the engagement context, the Envelope and the output folder. The AI Architect checks what comes back before it shows it to you as final (see After a build).

■The baseline-first rule

No specialist proposes, designs or creates a custom table, a custom scoped app, a custom state, a custom Connection & Credential Alias or another major custom object without your explicit, separate approval. The baseline is always looked at first, and preferred.

When a request needs one, the reply stops at a block titled OPEN QUESTION — CUSTOM OBJECT PROPOSAL. In a domain covered by a gateway, it is Part 3 of the Envelope, with Verdict C. The block holds:

  1. the baseline option it looked at, and why it falls short;
  2. the custom object it proposes, at the smallest scope: a new field on a baseline table, then a table that extends a baseline table, then a table in an existing scoped app, and only then a new scoped app;
  3. what approving it costs: data model, deployment, support, upgrade risk;
  4. the alternatives if you reject it.

That reply holds no table model, field list, ACL matrix, code or diagram. Answer it in a separate message, for example:

  • Approved. Use a new table in the existing <scope> scoped app. — the work resumes, inside the scope you approved.
  • Rejected — use the baseline <construct>. — the design goes on with the baseline only; any gap becomes an open question.
  • Re-evaluate option 2 more carefully — I think there's a baseline path. — the gateway looks again with your hint.
  • Defer this feature to the next release. — it closes the thread.
Your request is not the approval

However detailed your first request is, it never counts as approval of a custom object: approve in a separate message that answers the open question. Your ruling is recorded as a decision record in the engagement's decisions folder. If you ever see a field list or code in the same reply as this open question, the rule was bypassed: report it with /snowarch finding.

Each baseline claim in it names the documentation page it rests on, as (citation: markdown/<area>/<page>.md). A gateway is not a specialist you approve: it works in the same reply. ■Facts read from your instance

In live mode, before an Envelope is final, the AI Architect reads from your instance what the documentation cannot settle there: choice values, fields and their types, table parents, installed apps and plugins, assignment rules, SLA definitions, workspace pages. These reads change nothing and run without a permission question. By default it makes up to eight per Envelope, then says what it did not read. A fact read this way is cited as measured on instance <label>, <date>, and the reads are saved beside the Envelope, with the label and the date but never an address or an account. What is not a fact of the instance — what the business wants, who owns a step — stays an open question.

■Work that needs several specialists

The Integration Specialist owns the connection to the other system (REST or SOAP, spokes, MID Server, authentication, retries); the Flow Designer Specialist owns the orchestration (the trigger, the branches, the approvals); the Developer owns any JavaScript. A request that spans them is proposed as a sequence — Integration Specialist, then Flow Designer Specialist, then Developer — and each runs only after you approve the plan, one at a time, with the AI Architect checking each result before the next. Prompt pattern PP-13b asks for such a plan explicitly.

■After a build: reviews and proposals

Nothing is shown as final straight away. The AI Architect first checks the result for custom objects you did not approve (new tables, scopes, aliases, states or groups): if it finds one, the work goes back to the specialist before anything else. Then the domain gateway checks it against its Envelope. Then you get the result together with labelled proposals; you may decline each one, but it is always offered:

  • Code Reviewer, when the result holds JavaScript: Code artefact produced. Proposing a Code Reviewer pass (style, performance, security, best-practice) before final delivery — proceed? On yes it runs four checklists and rates each finding block, fix-before-prod or consider. For a block or a rework verdict it proposes to hand the result back to the builder, with the findings; say yes, and the checks run again afterwards. Keep this pass for anything meant for an instance.
  • ATF Author, when the result is meant for a release: Build artefact produced. Proposing ATF coverage before sign-off — single-component (skill) or full-app suite (sub-agent)?
  • Operational Documentation, when you mention going live (ready for prod, sign-off, release, go-live, cutover, deploy): Approaching production readiness. Proposing runbook + KBA authoring before go-live — proceed?
  • Diagramming Specialist, when a design returns: Design artefact produced. Proposing a Diagramming Specialist pass to render the architecture/process/data diagrams (editable draw.io with SVG/PNG export) before delivery — proceed?

Code-level security is the Code Reviewer's; architectural security — access rules, roles, data protection — is the Security & GRC Specialist's.

■Documents

A document, however short, is written by a specialist after your approval, never by the AI Architect itself: a design note, HLD, LLD or PDD by the HLD/LLD Writer; a runbook or a knowledge article by Operational Documentation. The AI Architect then renders its diagrams and its Word version as part of the delivery (see Deliverables).

■Deeper grounding

Claude can be switched to Ultracode or maximum effort for a session; that is a setting of Claude itself, not of the AI Architect. With it, the AI Architect may use parallel readers for grounding: it says so, says how many and how long, and reports as each finishes. In live mode its limit of eight instance reads per Envelope is then lifted, and it says how many it made. Without that setting it never does this.

Writing to an instance safely

Live mode is not permission to write. Every change on an instance is a separate decision that you approve, and every configuration change lands in an update set, so nothing is left outside change control.

■Two confirmations for every change

Before any call that changes the instance, the AI Architect asks exactly this, and waits:

Answer write approved. Then Claude shows its own permission question for that tool: every one of the 163 tools that change an instance is on Claude's ask list. Approve that too. The 236 tools that only read run without a question. Any other answer leaves the change unmade. After the change you get its result, with any warnings first.

What is not an approval

Your first request, however detailed (deploy it, go ahead); a yes to a routing or review proposal; an earlier general go-ahead that did not name this change; a yes to a read; switching to live mode, or raising a preset in your terminal; a request that lists the records. The AI Architect never infers approval from the context or the urgency.

The question takes three shapes:

  • One change: About to <action> on instance "<label>" — write approved?
  • A configuration change with its update set: About to <action> on instance "<label>", after ensuring update set <name> and pointing capture at it — write approved? One answer covers the update set and the change only when the question names them both; otherwise each is its own question.
  • Several records: one question per record, each answered before its own change; or, when one call writes several records, one question that names every record, in order.

■Stopped before the question

Before every change the AI Architect reads the instance's permissions. If one the tool needs is off, it stops without asking and shows what it read:

Nothing was called. Raise the preset in your terminal (see Permissions), then tell the AI Architect to go on: it reads the permissions again, with no restart. It never offers to change permissions or settings files from inside Claude.

■Update sets: every configuration change is captured

Before any change that makes a configuration object — a Script Include, Business Rule, Client Script, UI Policy, UI Action, ACL, flow, AI agent, agentic workflow, table or field — the AI Architect does four things, every time:

  1. It makes sure your own update set named <engagement>-<topic> is in progress, and creates it if it is not.
  2. It points capture at that update set (your user's update-set preference, which is what changes made this way follow).
  3. It makes the change, with its own approval.
  4. It looks into the update set to confirm the object is in it: that is the evidence.

You get the object's name, the confirmation that it is in the named update set, so it can be promoted, and any warnings. When you are ready to promote, export the update set as your release process says.

  • Steps 1 and 2 need WRITE and SCRIPTING (the pdi-developer or full preset). A read-only instance cannot capture.
  • Capture cannot be added afterwards. If steps 1 and 2 were skipped, the AI Architect stops and says so.
  • Background scripts are refused this way (UNSUPPORTED_ON_THIS_INSTANCE). Run such a script yourself in ServiceNow, in System Definition › Scripts - Background, or as a Fix Script, with a name of at most 40 characters.

A new release of the AI Architect comes from the place your folder was installed from. You move to it with one command, which shows a plan first and changes nothing until you accept it. Your instances, passwords, licence and client folders are not touched.

SNOW_ENV_FILE is not needed with the store. Do not set any other variable that starts with SNOWARCH_.

The system's own variables — PATH, HOME, SHELL, XDG_CONFIG_HOME; APPDATA, LOCALAPPDATA, USERPROFILE, the OneDrive ones — decide where the per-user store lives, where programs are found, and how commands are spelled in messages. You do not set them for the AI Architect. A window sees a changed PATH only once it is opened again.

Moving to a new computer, and removing the AI Architect

■Move to a new computer

Each AI Architect folder keeps its own state, so a new computer gets a fresh install. What is yours to carry over: your licence file, your clients folder (and any deliverables, memory or reports folder you made), the audit trail if you want to continue it, and your own entries in .claude/settings.local.json. Do not copy the rest of .local: it describes the old folder, and a copied install record makes the new install skip steps it needs.

  1. On the new computer, install the AI Architect with the install guide for that computer, at the same release.
  2. Put your licence in place (Renew your licence shows the copy command) and copy your clients folder into the new AI-Arch folder.
  3. Add each instance again with the wizard (Add an instance), typing the passwords again. That is this guide's advice. The product's own reinstall procedure (below) copies the store instead; if you copy it, the file holds your passwords in plain text: make it private again (chmod 600 .local/instances.json, or .\snowarch.cmd doctor --fix), and delete it from wherever it travelled.
  4. Run the full health check, and Status inside Claude: they should read as on the old computer.
  5. On the old computer, remove the AI Architect (below).

Your licence names no computer, but it is issued to you: if you are unsure whether your terms let you use it on a new or a second computer, ask your licence provider. Each computer has its own store: an instance you need on two computers is added on both. If you used the per-user store (--global), it lives outside the folder, in ~/.config/snowarch or %APPDATA%\snowarch: add those instances again too, and delete that folder on the old computer once no AI Architect folder there uses it.
